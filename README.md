# Методы классификации текстовых документов на основе дообучения большой языковой модели

Выпускная квалификационная работа. Задача — автоматическая маршрутизация входящей
корреспонденции крупного холдинга по **36 блокам**. Письма приходят в общий почтовый ящик и
сортируются вручную, что приводит к задержкам и потерям; цель работы — исследовать,
насколько для этой задачи применимо дообучение больших языковых моделей.

Основная сложность данных — сильный дисбаланс классов: исходный корпус содержит более
**1700 писем**, при этом часть блоков представлена единицами примеров, а крупнейший — почти
250. Поэтому работа состоит из двух частей: подготовка и аугментация данных, а затем
сравнение методов классификации на едином тестовом разбиении.

## 1. Данные и предобработка

Персональные данные в исходном корпусе заменены плейсхолдерами. При разведочном анализе
выявлены аномалии и дубликаты, поэтому реализован отдельный конвейер очистки
([`src/utils/data_cleaner.py`](src/utils/data_cleaner.py)): он удаляет точные и межклассовые
дубликаты, повторы слов, фраз и предложений, служебные цепочки вида «слово-число», обрезает
прицепленные к письмам приложения (таблицы, акты, договоры) и нормализует пробелы. После
очистки распределение длин писем стало симметричнее (среднее приблизилось к медиане), но без
потери содержательной части.

Отдельно проведён семантический анализ с целью выделить укрупнённые группы блоков —
текстовые метрики (доля уникальных слов, лексическое разнообразие), тематическое
моделирование на 30 темах и кластеризация по SBERT-эмбеддингам. Устойчивых семантических
групп выделить не удалось, поэтому работа с дисбалансом велась на уровне исходных 36 блоков.

## 2. Аугментация данных

Перед аугментацией корпус стратифицированно разбивается на обучающую и тестовую выборки
(80/20). Аугментируется **только обучающая часть**, а в качестве примеров для генерации
берутся исключительно оригиналы из неё. Это же разбиение используется во всех последующих
экспериментах — иначе сравнение методов было бы некорректным.

Аугментация проходит в три этапа; группа класса пересчитывается после каждого этапа, поэтому
блок, дотянутый до порога, переходит на следующий этап:

| Этап | Группа | Объём → цель | Метод |
|------|--------|--------------|-------|
| 1. Генерация | C | < 15 → 15 | LLM-генерация новых писем через vLLM |
| 2. Парафраз | B | 15–34 → 35 | Переформулирование оригиналов средствами LLM |
| 3. Обратный перевод | — | 35–49 → 50 | RU → en/de/fr → RU через NLLB-200 |
| (не трогаем) | A | ≥ 50 | — |

**Этап 1.** Для самых редких блоков модель (Qwen2.5-32B-Instruct-AWQ через vLLM) генерирует
новые письма. Перед генерацией для блока один раз создаётся его описание
(`generate_class_context`), которое вместе с несколькими реальными примерами подставляется в
промпт. Для блоков с 1–3 исходниками автоматически поднимается температура (0.9), иначе модель
скатывается в почти-копии.

**Этап 2.** Переформулируются именно **оригиналы**, а не синтетика первого этапа, чтобы не
накапливать каскад искажений. Каждый парафраз сохраняется в паре со своим оригиналом — чтобы
судья сравнивал именно эту пару.

**Этап 3.** Обратный перевод через три промежуточных языка (`eng_Latn`, `deu_Latn`,
`fra_Latn`) в несколько кругов с прогрессивным ослаблением порога сходства, чтобы добрать
упёртые классы.

Конфигурация LLM для аугментации вынесена в JSON ([`config_models/aug_configs/`](config_models/aug_configs/)):
основной — `model_vllm_32b.json` (Qwen2.5-32B-AWQ), плюс варианты на 14B / 7B / 3B. Каждый
этап сохраняет чекпоинт, поэтому прерванный прогон продолжается с места остановки.

### Валидация и LLM-судья

Каждый сгенерированный текст проходит **семь последовательных фильтров**
([`src/augmentation/validation.py`](src/augmentation/validation.py)), упорядоченных от дешёвых
к дорогим:

1. точные дубликаты (по `strip().lower()`);
2. минимальная длина (по умолчанию 500 символов при медиане оригинала ~1255);
3. язык — не-русский отсекается через `langdetect`;
4. вырожденность — доля уникальных слов < 0.2 или повторяющаяся фраза («модель залипла»);
5. CJK-символы — артефакт Qwen-моделей;
6. утечки промпта — мета-фразы, фрагменты системного промпта, разметка;
7. косинусное сходство по SBERT (`ai-forever/sbert_large_nlu_ru`) с **двусторонним** порогом:
   текст не должен быть ни почти-копией оригинала (верхний порог 0.95), ни искажённым до
   потери связи с классом (нижний 0.5). Верхний порог сужающийся.

Второй уровень контроля — **LLM-судья** с низкой температурой: он сравнивает оригинал и
сгенерированный экземпляр по заданным критериям (естественность, связность, соответствие
блоку) и выставляет оценку по шкале 1–10. Порог отсечения — **5 баллов** для генерации и
парафраза, **2.5** для обратного перевода. На этапе обратного перевода судья по умолчанию
отключён, поскольку на выходах NLLB он систематически занижает оценки и режет ~92% уже
прошедшего фильтры пула.

## 3. Базовый уровень классификации

Качество оценивается метриками **macro-F1** и **balanced accuracy** — они учитывают все блоки
с равным весом независимо от их размера. Базовый уровень получен на **трёх классических
моделях** на TF-IDF-признаках (LinearSVC, логистическая регрессия, наивный Байес) и **двух
энкодер-моделях**, предобученных на русском языке (rubert-tiny2 и rubert-base). Метрики
измерялись до и после аугментации — все модели улучшили результаты после расширения данных.

## 4. Проверка гипотез

### Гипотеза 1. Prompt-based классификация (few-shot)

Проверялось, способна ли готовая instruction-tuned LLM решать задачу без дообучения: модель
получает список 36 блоков, их описания и (опционально) примеры и возвращает название блока.
Реализован отдельный пайплайн ([`scripts/run_few_shot.py`](scripts/run_few_shot.py));
наибольшую сложность в нём представляла **система извлечения ответа**
([`prompt_classifier.py`](src/classification/prompt_classifier.py)) — каскад от точного
совпадения до нечёткого матчинга через `difflib`, поскольку модель редко отвечает односложно
даже при низкой температуре.

Матрица экспериментов — модели × режимы:

| Модель | HF-идентификатор | Контекст | Движок |
|--------|------------------|----------|--------|
| `saiga_8b` | `IlyaGusev/saiga_llama3_8b` | 8k | transformers |
| `t_lite_8b` | `t-tech/T-lite-it-1.0` | 32k | transformers |
| `vikhr_12b` | `Vikhrmodels/Vikhr-Nemo-12B-Instruct-R` | 32k | transformers |
| `qwen_14b` | `Qwen/Qwen2.5-14B-Instruct` | 32k | transformers |
| `qwen_32b` | `Qwen/Qwen2.5-32B-Instruct-AWQ` | 32k | vLLM, AWQ |

| Режим | K | Описания классов |
|-------|---|------------------|
| `0` | 0 | да (baseline без примеров) |
| `1` | 1 | да |
| `3` / `3nd` | 3 | да / **нет** |
| `5s` / `5snd` | 5 | да / **нет** |

Режимы без описаний (`*nd`) измеряют вклад описаний классов отдельно от примеров. Лучший
результат показала наиболее крупная модель (Qwen, 32 млрд параметров), однако все модели
существенно уступили базовому уровню. Вывод: на имеющихся данных prompt-based подход
непригоден.

### Гипотеза 2. Дообучение LLM (PEFT)

Основная часть работы. Реализован единый конвейер дообучения (`SeqClsRunner`,
[`src/finetune/trainer_base.py`](src/finetune/trainer_base.py)):

1. загрузка данных, подсчёт весов классов, выделение валидационной выборки (`val_split`);
2. загрузка базовой модели и квантизация при необходимости (для QLoRA — NF4 + double quant);
3. подключение к замороженной модели **низкорангового адаптера** и **классификационной
   головы**;
4. обучение с проверкой на валидации после каждой эпохи; лучший чекпоинт сохраняется по
   `eval_macro_f1`, плюс early stopping (`patience = 2`);
5. оценка на том же тестовом разбиении, что и в остальных экспериментах.

**Один JSON-конфиг = один прогон**
([`config_models/finetune_configs/`](config_models/finetune_configs/)). Конфиг
самодостаточен — модель, метод, гиперпараметры и флаги в одном файле:

```json
{
  "run_key": "qwen3_32b_qlora_cw",
  "model_name": "Qwen/Qwen3-32B",
  "method": "qlora",              // qlora / lora / adalora / tinylora
  "num_labels": 36,
  "use_class_weights": true,      // балансировка loss по обратной частоте классов
  "val_split": 0.10,
  "peft_config":   { "r": 16, "lora_alpha": 32, "target_modules": ... },
  "quantization":  { ... },       // только для QLoRA
  "training_params": { "num_train_epochs": ..., "lr": ..., ... }
}
```

GPU-специфика (`per_device_batch`, `grad_accum`, `max_seq`, `bf16/fp16`) вынесена в
`pipeline_config.json` под профили **T4 / L4 / A100-40 / A100-80 / H100** и накладывается
поверх `training_params` автоматически — конфиг прогона не зависит от железа и выбирается
флагом `--gpu`.

При `use_class_weights: true` вектор весов считается по sklearn-формуле
`w[c] = n_samples / (n_classes · count[c])` и подставляется в `CrossEntropyLoss` — ошибка на
малочисленном блоке «стоит» дороже, что заставляет модель учитывать редкие классы.

Сравнивались **восемь открытых моделей** от 8 до 32 млрд параметров — разных семейств и
степени адаптации к русскому языку:

| Модель | Параметры | Адаптация к русскому |
|--------|-----------|----------------------|
| Qwen3-32B, Qwen2.5-32B | 32B | базовая (мультиязычная) |
| Qwen3-14B | 14B | базовая |
| T-pro-it-2.1 | 32B | T-Bank, на базе Qwen3 |
| RuadaptQwen3-32B | 32B | LLaMA-Ru-адаптация |
| Vistral-24B | 24B | русскоязычная |
| Vikhr-Nemo-12B | 12B | русскоязычная |
| YandexGPT-5-Lite | 8B | русскоязычная |

Каждая модель прогонялась по **четырём методам дообучения** (QLoRA, LoRA, AdaLoRA, TinyLoRA),
с балансировкой классов и без неё, с варьированием ранга адаптера (r=16 против r=32) —
итерационная матрица `iter1…iter4_cw`, где последний круг включает class_weights.

Все дообученные модели превзошли базовый уровень. Лучшая конфигурация по совокупности метрик
дала **+7% по macro-F1** и **+6% по balanced accuracy** относительно базового уровня;
наилучшим методом оказался **QLoRA** — даже для большинства небольших моделей, где
рассматривался LoRA. По наблюдениям матрицы: Qwen3-32B комфортнее с r=16, T-pro-it-2.1 —
наоборот, с r=32, а пик по эпохам почти везде приходится на третью.

Конвейер передан научному консультанту, и на немаскированных данных дообученные модели также
обошли базовый уровень.

## 5. Запуск

```bash
pip install -r requirements.txt

# аугментация + базовый уровень
python scripts/augmentation.py --gpu A100_40

# few-shot: все модели и режимы (или подмножество через --models / --experiments)
python scripts/run_few_shot.py

# один прогон дообучения
python scripts/run_finetune.py --config qwen3_32b_qlora_cw.json --gpu A100_40
```

Прогоны идемпотентны — повторный запуск подхватывает уже посчитанное и досчитывает
недостающее. Каждый прогон дообучения пишет метрики в `results/finetune/<run_key>.json`;
сводка по всем методам собирается в `results/all_methods_comparison.csv`, графики top-N — в
[`notebooks/aggregate_results.ipynb`](notebooks/aggregate_results.ipynb). Для кластера есть
SLURM-обёртки в `scripts/slurm/` (`*_pre` / `*_run` / `*_post`), для интерактивной работы —
ноутбуки в `notebooks/` (заводятся в Colab).
